# Grain Check

An offline execution-based evaluation for SQL generated by a model or written by hand. Three retail analytics questions run against three independent SQLite fixtures. Expected rows are computed from the input records in Python. Comparison preserves duplicate rows and ignores row order.

## Run

From this directory, with Python 3.9 or newer:

```sh
python grain_check.py
python grain_check.py --suite reference --require-pass
python grain_check.py --suite reference --json
```

The deliberately flawed hand-written baseline passes 1/9 checks. The hand-written reference passes 9/9. These scores illustrate evaluation behavior and do not measure any model.

## Evaluate your own queries

The sales table has columns `product TEXT, units INTEGER, returned INTEGER, price_cents INTEGER`. Each row represents a sale. Give your model the schema and the following questions, then save its SQL in a JSON object using these keys:

| Key | Requested result |
| --- | --- |
| return_rate | Product with highest total returned units divided by total units sold, breaking ties alphabetically. One product column. |
| net_revenue | Sum of revenue in cents for retained units. One integer column. |
| repeat_products | Names of products present in at least two sales rows. One product column. |

```sh
python grain_check.py --candidates candidates.json --require-pass
```

Each query runs on a fresh in-memory database. A query error or a wrong answer fails its fixture. Use `--json` for the full evidence including SQL, source rows and expected answers.

## A failure you can inspect

In the launch fixture, Atlas returned 8 of 102 units. Orbit returned 4 of 10. Ranking by return count picks Atlas, while ranking by rate picks Orbit. In the uneven fixture, both queries pick Flux. A single passing fixture can hide the error.

These nine synthetic checks cover a narrow schema. Use additional fixtures and questions before drawing conclusions about a production model.
